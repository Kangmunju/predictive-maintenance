# 설비 예지보전 (Predictive Maintenance) — 센서 파이프라인부터 대시보드까지

**CNC 밀링 설비의 센서 데이터를 수집·정제하고, 30분 내 고장을 예측합니다.**

수집 파이프라인(GitHub Actions 자동화)부터 모델 평가, 에피소드 단위 알람 분석, 대시보드 배포까지 전 구간을 구성했습니다.

🔗 **[대시보드 바로가기](https://predictive-maintenance-8nwm5s6qwq8j8j6rj9tbkg.streamlit.app/)** · 📄 **[분석 리포트](reports/analysis_report.md)**

## 30초 요약

| 항목 | 내용 |
|---|---|
| **문제** | 설비 고장을 **사후 감지**가 아니라 **30분 전 예지** — 계획 정비를 위한 고장 위험 예측 |
| **데이터** | ① 물리 기반 시뮬레이터 및 자동수집 합성 데이터 ② UCI AI4I 2020(10,000행) ③ UCI SECOM(1,567행 × 590센서) |
| **방법** | 수집 → 정제(9단계) → 피처 100개 → RandomForest → 시간순 데이터 분할 → 비용 기반 임계값 → 에피소드 평가 |
| **최신 모델 결과** | **AP 0.7664**, 양성률 기준선 0.2157, 단순 이력 규칙 AP 0.3707, ROC-AUC 0.9047 |
| **운영 평가** | 고장 에피소드 190건 중 150건 탐지(**78.95%**), 독립 알람 490건, 오경보 339건 |
| **핵심 발견** | 랜덤 split PR-AUC **0.9819** → 시간순 split **0.7589**. 시간적 의존성을 무시하면 성능이 과대평가될 수 있음 |
| **한계** | 합성 데이터, 가정한 비용, 테스트 구간에서 임계값 선택, 전처리 및 학습·평가 경계의 데이터 누수 가능성 |

### 성능 수치의 데이터 기준

서로 다른 데이터셋과 실행 시점에서 얻은 결과를 구분했습니다.

| 평가 대상 | 평가 방식 | AP | 양성률 기준선 | 실행 스크립트 |
|---|---|---:|---:|---|
| **현재 자동수집 합성 데이터** | 기존 코드의 75:25 행 기준 분할 | **0.7664** | 0.2157 | `src/train.py` |
| 이전 자동수집 합성 데이터 | 기존 코드의 75:25 행 기준 분할 | 0.7688 | 0.2279 | `src/train.py` |
| 14일 연속 시뮬레이션 | 시간순 분할 | 0.7589 | 별도 확인 필요 | `analysis/a3_leakage.py` |
| 14일 연속 시뮬레이션 | 랜덤 분할 | 0.9819 | 별도 확인 필요 | `analysis/a3_leakage.py` |

- 현재 자동수집 데이터의 결과는 `models/metrics.json`을 기준으로 작성했습니다. 데이터 추가 또는 재학습 시 수치가 달라질 수 있습니다.
- 현재 모델 평가에 사용된 행 수는 **177,339행**이며, 초기 14일 시뮬레이션의 학습용 데이터 53,811행과 구분해야 합니다.
- AP(Average Precision)는 `average_precision_score`로 계산한 값입니다. 프로젝트에서 PR-AUC로 표기한 지표는 이 AP를 의미합니다.
- 14일 연속 시뮬레이션의 분할 비교 실험은 자동수집 데이터 평가와 별개이므로 수치를 직접 비교하지 않습니다.
- 현재 파이프라인은 시간순으로 정렬한 뒤 행 수 기준 75:25로 나누므로, 같은 시각의 서로 다른 설비 데이터가 학습·평가 구간에 걸칠 수 있습니다.
- 전처리 기준과 30분 미래 라벨의 경계 처리에도 데이터 누수 가능성이 남아 있습니다.
- 시뮬레이터 및 자동수집 데이터는 **합성 데이터**이므로 실제 설비에서 동일한 성능을 보장하지 않습니다.

## 왜 이 주제인가

스마트팩토리 환경에서는 설비 센서 데이터가 시간에 따라 연속적으로 수집되기 때문에 일반적인 정형 데이터 분석과 다른 문제가 발생할 수 있습니다.

이 프로젝트에서는 단순히 모델 성능을 높이는 것보다 **제조 센서 데이터를 다룰 때 발생할 수 있는 함정을 직접 검증하는 것**에 초점을 맞췄습니다.

## 핵심 결과 4가지

### 1. 정확도만으로는 불균형 모델을 평가할 수 없다

AI4I 데이터의 고장률은 약 3.39%입니다.

모든 데이터를 정상으로 예측해도 높은 정확도가 나오지만 고장을 하나도 찾아내지 못합니다.

| 모델 | 정확도 | 재현율 | PR-AUC |
|---|---:|---:|---:|
| 무조건 "정상" | **약 0.966** | 0.000 | 약 0.034 |
| 랜덤포레스트 | 약 0.982 | 약 0.576 | 약 0.789 |
| 랜덤포레스트 + 도메인 파생변수 | 약 0.993 | 약 0.824 | **0.897** |

→ 불균형 데이터에서는 정확도뿐 아니라 **PR-AUC와 고장률 기준선을 함께 확인**해야 합니다.

### 2. 시간 누수 — 랜덤 split이 만든 과대평가

같은 데이터와 모델을 사용하고 **데이터 분할 방식만 변경**해 비교했습니다.

| split | ROC-AUC | PR-AUC | F1@0.5 |
|---|---:|---:|---:|
| 랜덤 split | 0.9954 | **0.9819** | 0.9358 |
| 시간순 split | 0.8956 | **0.7589** | 0.6771 |

랜덤 split에서는 test 데이터와 가장 가까운 train 데이터의 시간 거리가 **중앙값 0분**이었습니다.

시뮬레이터의 예측 라벨은 앞으로 30분 내 고장 여부를 사용하기 때문에, 시간적으로 가까운 데이터를 무작위로 나누면 학습 구간과 평가 구간 사이의 의존성이 매우 커집니다.

반면 AI4I 데이터에서는 시뮬레이터와 달리 시간적 자기상관이 거의 없었고 랜덤/시간순 분할에 따른 차이도 상대적으로 작았습니다.

→ **시간적 의존성과 실제 운영 시점의 예측 구조를 고려해 분할 방법을 정해야 합니다.**

### 3. 임계값 0.5가 항상 최적인 것은 아니다

고장을 놓쳤을 때의 비용을 **800만원**, 불필요한 점검 비용을 **30만원**으로 가정해 임계값별 총비용을 비교했습니다.

아래는 기존 `analysis/a6_cost_threshold.py` 실험 결과입니다.

| 기준 | 임계값 | 재현율 | 정밀도 | 총비용 |
|---|---:|---:|---:|---:|
| 기본 임계값 | 0.50 | 약 0.824 | 약 0.959 | 12,090만원 |
| **비용 최소** | **0.06** | **0.929** | 0.444 | **7,770만원** |

가정한 비용 구조에서는 0.5보다 낮은 임계값을 사용할 때 고장 누락을 줄여 총비용을 낮출 수 있었습니다.

F1이 최대인 지점과 비용이 최소인 지점도 서로 달랐습니다.

→ 실제 운영에서는 **고장 누락 비용과 점검 비용을 반영해 의사결정 임계값을 정해야 합니다.**

### 4. 행 단위 성능과 실제 알람 운영 성능은 다르다

기존 분류 평가는 매 시각의 예측을 개별 행으로 평가합니다.

하지만 실제 설비 운영에서는 동일한 고장을 앞두고 여러 번 경고가 발생하더라도, 이를 독립적인 고장 탐지 성공으로 반복 계산해서는 안 됩니다.

이를 보완하기 위해 `src/episode_eval.py`에서 **고장 에피소드와 독립 알람 그룹**을 기준으로 평가했습니다.

#### 최신 모델의 AP 비교

| 평가 기준 | AP |
|---|---:|
| 테스트 양성률 기준선 | 0.2157 |
| 과거 30개 관측치의 고장 이력 비율 | 0.3707 |
| **RandomForest** | **0.7664** |

RandomForest의 AP는 단순 이력 규칙보다 **0.3957p** 높았습니다.

다만 단순 이력 규칙은 과거의 실제 고장 라벨을 사용하므로, 고장 확인이 지연되는 운영 환경에서는 같은 방식으로 즉시 사용할 수 있다는 보장이 없습니다.

#### 에피소드 및 독립 알람 평가

평가 기준:

- 고장 에피소드 및 사전 탐지 구간: 30분
- 연속된 경고를 하나의 독립 알람으로 묶는 간격: 10분
- 현재 모델 평가 임계값: **0.03**

| 지표 | 임계값 0.03 | 임계값 0.50 |
|---|---:|---:|
| 고장 에피소드 | 190건 | 190건 |
| 탐지 성공 | **150건** | 130건 |
| 미탐지 | 40건 | 60건 |
| 에피소드 탐지율 | **78.95%** | 68.42% |
| 독립 알람 | 490건 | 233건 |
| 오경보 | 339건 | **102건** |
| 일평균 오경보 | 28.94건 | **8.71건** |
| 에피소드 기준 총비용 | **421,700,000원** | 510,600,000원 |

임계값을 0.50에서 0.03으로 낮추면 탐지 성공 에피소드는 **20건 증가**하지만, 오경보도 **237건 증가**합니다.

가정한 비용 기준으로 에피소드 총비용은 **88,900,000원 감소**했습니다.

이는 단순히 재현율을 높이는 것만으로는 충분하지 않으며, **탐지율·오경보 빈도·운영 비용을 함께 평가해야 한다**는 점을 보여줍니다.

#### 행 단위 비용과 에피소드 단위 비용의 차이

| 평가 단위 | 임계값 0.03 | 임계값 0.50 |
|---|---:|---:|
| 행 단위 비용 | 8,595,200,000원 | 28,853,500,000원 |
| 에피소드 단위 비용 | 421,700,000원 | 510,600,000원 |

행 단위 비용은 개별 시점의 오분류를 집계하고, 에피소드 단위 비용은 고장 사건과 묶인 알람을 기준으로 집계합니다.

따라서 **두 비용은 집계 단위가 달라 금액을 직접 비교할 수 없습니다.**

현재 임계값 0.03은 **테스트 구간의 행 단위 비용을 기준으로 선택**한 값입니다. 에피소드 비용을 별도로 최적화한 값은 아니며, 동일한 테스트 데이터에서 임계값을 선택하고 성능을 평가했으므로 낙관적 편향 가능성이 있습니다.

## 정제 처리 이력

원본 데이터를 바로 모델에 넣지 않고, 중복·물리 범위·시간축 문제를 단계별로 확인했습니다.

다음 수치는 **초기 14일 시뮬레이션 데이터의 정제 결과**입니다.

| 단계 | 행 수 | 증감 | 설명 |
|---|---:|---:|---|
| 0. 원본 수신 | 55,591 | — | 14개 일별 CSV |
| 3. 중복 제거 | 53,874 | -1,717 | `(machine_id, ts)` 기준 |
| 5. 물리범위 위반 → NaN | 53,874 | 0 | 행을 삭제하지 않고 해당 값만 NaN 처리 |
| 9. 시간축 재색인 | 60,479 | +6,605 | 통신 공백을 명시적인 NaN 행으로 표현 |

정제 후 학습용 데이터에서는 피처와 30분 미래 라벨을 생성할 수 없는 구간 등을 제외해 **53,811행**을 사용했습니다.

### 센서 값 정제 개선

온도 센서의 단위 혼입과 비정상적인 0값을 구분하도록 정제 순서를 개선했습니다.

- 온도·센서 값 중 비정상적인 0값을 결측치(NaN)로 변환
- 섭씨로 기록된 것으로 판단되는 온도 값(0.1~60)을 켈빈으로 변환
- 단위 변환 후에도 200K 미만인 비정상 온도는 결측치로 처리
- **단위 변환 이후 물리 범위 검사**를 수행해 정상적인 섭씨 데이터가 이상치로 잘못 분류되는 문제 방지

## 자동 수집 및 대시보드

GitHub Actions를 이용해 센서 데이터를 자동 수집하고 저장소의 `data/history/`에 일별 CSV 형태로 누적합니다.

수집 이후 모델 학습을 실행하고 `models/`의 성능 지표와 예측 결과를 갱신합니다.

Streamlit Cloud에서는 모델을 직접 재학습하지 않고, 저장된 CSV/JSON을 읽어 시각화합니다.

대시보드는 다음 네 가지 탭으로 구성했습니다.

| 탭 | 주요 기능 |
|---|---|
| 운영 현황 | 설비별 센서 추이, 고장 관련 지표, 데이터 존재 일수 |
| 데이터 품질 | 센서별 결측률, 통신 공백 확인 |
| 모델 성능 | AP 기준선 비교, 분류 지표, 에피소드 탐지율, 오경보, 비용 비교 |
| 방법·한계 | 데이터 생성 및 평가 방법, 합성 데이터와 검증상의 한계 |

### 데이터 존재 일수 계산

2024년 초기 시뮬레이션 데이터와 2026년 자동 수집 데이터가 함께 저장되어 있습니다.

단순히 최초 날짜와 최종 날짜의 차이를 계산하면 **데이터가 존재하지 않는 중간 기간까지 수집 기간에 포함**됩니다.

이를 방지하기 위해 `ts.dt.normalize().nunique()`를 사용하여 실제 관측 데이터가 존재하는 날짜만 계산합니다.

2026년 10월 10일 로컬 확인 기준:

- 일별 CSV 파일: **44개**
- 최초 데이터: **2024-01-01 00:00**
- 최종 데이터: **2026-10-10 00:22**
- 실제 데이터 존재 일수: **49일**

CSV 파일 수와 데이터 존재 일수는 반드시 같지는 않으며, 자동 수집이 계속되면 위 값도 변경됩니다.

대시보드에서 사용하는 설비 데이터는 물리 기반 시뮬레이터로 생성한 **합성 데이터**입니다.

## 한계와 가정

### 데이터의 한계

- **시뮬레이터 데이터는 합성 데이터입니다.** 모델의 성능을 실제 제조 설비에 그대로 적용할 수 없습니다.
- 시뮬레이터의 고장 규칙이 결정론적이기 때문에 실제 설비보다 예측이 쉬울 수 있습니다.
- 초기 실험은 14일 × 3대 데이터이며, 이후 자동수집 데이터를 추가했더라도 장기적인 설비 열화와 계절성을 충분히 검증한 것은 아닙니다.
- 2024년 초기 실험과 2026년 자동 수집 사이에 데이터가 없는 기간이 존재합니다.
- AI4I 데이터에는 RNF 라벨과 전체 고장 라벨 사이에 일부 모순이 존재합니다.

### 방법의 한계

- **고장 누락 800만원, 불필요한 점검 30만원이라는 비용은 실제 기업 데이터가 아닌 가정값입니다.**
- 비용 구조가 달라지면 최적 임계값 역시 달라집니다.
- 현재 비용 기반 임계값은 테스트 데이터에서 탐색했기 때문에 낙관적 편향 가능성이 있습니다.
- 행 단위 비용과 에피소드 단위 비용은 집계 기준이 달라 직접 비교할 수 없습니다.
- 시간순 분할을 사용하지만, 동일 시각 데이터의 경계 중복 및 미래 라벨 생성 구간에 따른 누수 가능성이 남아 있습니다.
- 전처리 과정에서 전체 데이터의 통계량을 활용하는 경우 학습·평가 구간 사이의 정보 누수가 발생할 수 있습니다.
- 시간순 split을 한 번만 사용했습니다. 실제 적용에서는 검증 구간을 별도로 두고 walk-forward 방식 등을 이용한 반복 검증이 필요합니다.
- 단순 이력 규칙은 과거의 실제 고장 여부를 활용하므로 운영 환경에서 고장 라벨의 확인 시점을 고려해야 합니다.
- 드리프트 보정 효과가 잡음에 의한 변화인지 명확히 구분하기 어렵습니다.

### 해석의 한계

- 상관관계가 있다고 해서 인과관계가 있다는 의미는 아닙니다.
- RandomForest의 변수 중요도는 모델이 예측에 많이 사용한 변수를 보여줄 뿐, 설비 고장의 물리적 원인을 증명하지 않습니다.
- SECOM의 낮은 성능은 **현재 사용한 데이터와 방법으로 충분한 예측력을 확보하지 못했다는 의미**이며, 반도체 공정 불량 예측 자체가 불가능하다는 의미는 아닙니다.

---

## SECOM에서 성능이 나오지 않은 이유

SECOM 데이터는 **1,567행에 590개 센서**가 존재하는 고차원·저표본 데이터이며 불량은 104건뿐입니다.

분석 과정에서:

- 상수 센서 116개 제거
- 정제 후 446개 센서 사용
- 단변량 검정 p<0.05 센서 79개
- Bonferroni 보정 후 6개
- BH 보정 후 22개
- 시간순 평가 PR-AUC **0.0833**
- 기준선 약 **0.0612**

를 확인했습니다.

또한 시간에 따라 센서 분포가 크게 이동하는 현상이 나타났습니다.

따라서 성능 수치를 억지로 높이기보다 **추가 불량 사례, 센서 의미에 대한 메타데이터, 공정 단계, 설비 변경 이력 등이 필요하다**고 판단했습니다.

## 무엇을 배웠나

1. **불균형 데이터에서는 정확도만으로 모델을 평가할 수 없다.**  
   PR-AUC와 고장률 기준선을 함께 확인해야 모델의 실제 분류 능력을 판단할 수 있었습니다.

2. **시간적 의존성을 무시한 데이터 분할은 성능을 과대평가할 수 있다.**  
   랜덤 split과 시간순 split을 직접 비교하면서 예지보전 문제에서 평가 방법 자체가 모델만큼 중요하다는 것을 확인했습니다.

3. **모델의 최적 기준은 평가 지표 하나로 결정되지 않는다.**  
   고장 누락과 불필요한 점검의 비용이 다르기 때문에 운영 목적에 맞는 임계값이 필요했습니다.

4. **행 단위 예측 성능이 곧 실제 운영 성능은 아니다.**  
   고장 에피소드와 독립 알람을 기준으로 다시 평가하면서 탐지율, 오경보, 비용의 상충 관계를 확인했습니다.

5. **좋은 결과가 나오지 않은 데이터도 분석 결과다.**  
   SECOM에서 낮은 성능을 확인하고, 표본 수·고차원성·분포 이동 등 성능을 제한하는 원인을 분석했습니다.

6. **데이터의 범위와 실제 데이터가 존재하는 기간은 구분해야 한다.**  
   서로 떨어진 기간의 데이터를 함께 다룰 때 단순 날짜 차이만으로 수집 일수를 계산하면 잘못된 운영 지표가 만들어질 수 있음을 확인했습니다.
